# Settle visual system — implementation audit and coverage

## Audit (before changes)

The shell and legacy payout UI used blue actions, grey outlines and a separate system font declaration; transaction, allocation and AG surfaces used a different green palette, with repeated hex values and different card/control proportions. The three stylesheets mixed brand colors with functional green, amber, red and blue. AG Grid, Studio and Charts already used supported theme APIs, but their theme was independent of most CSS. Workspace forms used native controls. The application defaults to verified transactions; navigation also reaches allocation, workspace and legacy payout, while landing and result are conditional. `operations/` UI is not imported by the application entry graph. The repository provides Vitest, Node tests and Playwright, but no dedicated accessibility or visual-baseline runner.

## Architecture and use

`app/src/ag/theme.ts` is the current authoritative source for brand, neutrals, status pairs, chart palette and shared AG geometry. `primitives` hold values; `semanticTokens` defines roles and `componentTokens` maps shared component decisions to those roles; `settleTokens` supplies compatibility aliases for existing AG consumers; `settleGridParams`, `settleStudioParams` and `settleChartTheme` adapt them through the supported AG APIs. `applyDesignTokens`, invoked by `ag/setup.ts` before React mounts, publishes CSS custom properties. Example: `color: var(--settle-ink); background: var(--settle-surface);`. Do not paste brand hex values into components; `brand-guard.test.ts` checks the three approved values outside the source. Reuse an existing role before adding a primitive; add a component alias only when it expresses a real component-specific decision. Change a shared color in `primitives`, not in individual screens.

Inkberry anchors the interface; Haze supports subdued text on dark surfaces; Citrus identifies selection and high-emphasis actions, not payment success. Financial statuses retain labelled functional tones: success, warning/pending, danger, information and neutral. Provider confirmation, reconciliation, submitted, unknown, sample and historical evidence must retain their existing text and provenance; never infer success from an action or color. Chart colors are categorical and cannot be the sole carrier of meaning.

System typography is system-ui, with tabular figures on key metrics; spacing properties `--settle-space-0` through `--settle-space-7` span 0–48px. Shared radius, border and surface properties are published alongside them. Controls inherit the font, have visible focus rings and disabled styling. Primary actions use ink on light surfaces; secondary actions use a surface and border; active navigation is citrus. Inputs have a strong boundary and focus ring; errors use a labelled alert. Cards use a surface and restrained boundary. Tables and Studio use their supported theme parameters. Interactive states must remain labelled, including loading, error and empty cases. Existing breakpoints are 850px for transaction/allocation stacking and 600px for compact page, navigation and toolbar layout. Motion is suppressed under reduced-motion preferences.

Common existing margin, padding and gap values on the shared spacing scale now use the published tokens without changing their initial computed sizes. A browser test confirms shell and navigation respond to token changes. The three layers are present, but migration remains incremental: some dimensions and component states still use local values; not every component consumes a component alias. Systematic keyboard review, graphical contrast, broader color-vision review and a full accessibility audit remain work. Existing contrast tests check core text/status pairs, not WCAG conformance. Avoid claiming compliance until full testing, including focus and interactive boundaries, has been performed.


### Component state rules

- **Buttons:** primary uses the button role token; secondary uses a surface and strong border. Hover darkens the primary; focus is visibly outlined; disabled controls remain labelled and unavailable. Loading actions retain explanatory text (for example “Evaluating…”); never treat completion of a request as payment confirmation.
- **Fields:** use a label or accessible name, a strong boundary and visible focus. Errors must be text associated with the operation; disabled/read-only fields must remain legible and distinguishable. The current application does not yet provide a shared error/read-only input variant.
- **Badges and alerts:** success is reserved for recorded success; pending uses warning, failed/danger uses danger, and unknown/unverified use their explicit labels and appropriate warning or neutral tone. Preserve the specific source and evidence text, not just the color.
- **Cards and tables:** standard surfaces use card/background and border roles; selected rows and navigation use a selection treatment plus an explicit state. Tables should preserve horizontal access on narrow screens and keep amounts tabular. Elevated overlays should use the elevated surface and stacking convention when such a component is introduced.

- Axe WCAG-tagged smoke scans of four default product views reported no violations in the rendered fixtures. After upgrading AG Grid 36.3, Charts 14.3 and Studio 3.1, collapsed showcase master/detail scans pass at three widths without an exception. Expanded detail also passes after the custom renderer supplies the gridcell role required by its parent row. These targeted scans are not a compliance certification. The pin change is Parv's named decision when he commits.
- An authenticated stack-fixture workspace was also rendered at desktop, tablet and mobile widths; three screenshot/overflow and axe checks passed. It uses the scripted provider, and the test does not initiate payments.
- Transaction evidence, investigation-error, analytics and empty states were captured at desktop, tablet and mobile widths; the evidence/error state passed axe scans at all three widths. The mobile screenshot was visually inspected. On mobile the horizontally constrained grid uses the existing row selection and “Open selected” control to inspect a record.

- Fixture screenshots are in `evidence/design-system/`; they are not provider evidence. Screenshot tests check root overflow, not clipping within each component. Screenshots are not approved visual regression baselines.
- Chromium protanopia, deuteranopia and tritanopia simulations were captured for the transaction fixture; tests assert visible status labels, and the deuteranopia screenshot was visually inspected. These checks are not a comprehensive color-vision audit. No exhaustive keyboard audit or visual regression comparison was run. Full desktop/tablet/mobile verification of every conditional state and all isolated component states remains outstanding. The legacy Studio internal-cell CSS override was replaced with the supported Studio widget renderer hook; the stack test checks that renderer and fallback.
